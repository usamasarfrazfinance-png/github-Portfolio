Case Study 01 · Banking

Commercial Bank of Qatar

Maintaining, troubleshooting, and modernising a highly customised Dynamics 365 CRM On-Premises deployment tied directly into the bank's core banking systems.

Overview

Commercial Bank of Qatar runs a heavily customised, on-premises Dynamics CRM installation wired directly into its core banking system and several backend services. My work here wasn't a single project with a clean start and end; it was ongoing maintenance, troubleshooting, and modernisation of critical banking processes across the full technical stack: plugins, custom workflows, JavaScript, integrations, SQL, and the CRM UI itself.

Customer cases and banking service requests

I worked extensively on the Customer Cases module that handles day-to-day banking service requests: dishonoured cheques, full loan settlement, credit card queries, and debit card queries. Rather than patching individual screens, I traced these processes end to end, from JavaScript and plugins through workflows, approvals, and Business Process Flow stages, so cases could move from initiation to completion without stalling partway through.

For dishonoured cheques specifically, I worked with a custom AG Grid component used to retrieve, display, select, and process cheque records inside CRM.

Customer onboarding and account opening

The onboarding process, what runs when a new customer joins the bank and an account gets opened, had grown very complex over time. Depending on customer type, the CRM form was firing more than 40 JavaScript functions on load: showing and hiding tabs, controlling BPF stages, switching forms, pulling values from related entities, applying customer-specific rules, and kicking off downstream integrations.

I audited that implementation and consolidated the JavaScript logic, keeping every piece of required functionality while cutting the redundant processing. That brought form-load time down and made the whole thing easier to maintain going forward. I also fixed integration and approval issues at specific BPF stage transitions so data updates and stage changes ran correctly across the full onboarding lifecycle.

Core banking and API integrations

CRM processes needed live data from the core banking system, both reading customer and account information and, in some cases, writing updates back. I worked the CRM side of that integration: retrieving data from backend services, processing responses, mapping values into CRM, and troubleshooting failures to make the integration flow more reliable.

I was also part of migrating existing integrations from ESB to KONG, which meant reworking the CRM integration layer so existing processes and APIs could route through KONG without breaking any banking business logic already in place.

Plugin consolidation

The environment had accumulated a large number of plugins, including cases where several plugins were registered on the same message, pipeline, and trigger, all firing for overlapping scenarios. I reviewed these and merged related plugins into consolidated components, adding conditional logic so a single implementation decided what needed to run for a given case instead of multiple plugins executing unnecessarily. That reduced execution overhead and cut the risk of conflicts between different pieces of server-side logic.

SQL, stored procedures, and reconciliation

My work went past the CRM application layer into the database itself. I investigated and modified stored procedures called from CRM to make sure the right data was being retrieved, which meant understanding both the CRM-side implementation and the SQL underneath it rather than treating CRM as a black box.

During an environment migration, I also built a reconciliation reporting process: SQL queries comparing configuration data between the old production server and the new pre-production server, surfacing old value, new value, and what had changed so the team could verify and sign off on the migration systematically rather than checking values by hand.

Custom dashboards and legacy UI work

I built the JavaScript integration layer for a custom HTML/CSS dashboard, handling the calls to backend services, processing the returned data, and populating the dashboard dynamically, including transforming raw values into the shape the business actually needed before displaying them.

On the AG Grid side, several older implementations required a manual button click before a grid would load its records. I automated that so data loaded as soon as the relevant record or form opened. I also worked with custom HTML-based fields used to surface information that the underlying CRM schema couldn't display natively, mapping and rendering the right values without disturbing the existing data model.

What this added up to

Across all of it, the objective was the same: make the CRM solution faster, more stable, and less error-prone, while making sure the integrations with core banking and other backend systems kept working correctly through the entire business process. That meant getting comfortable with legacy, sometimes undocumented implementations, finding where they were actually failing, and fixing them without putting live banking operations at risk.
